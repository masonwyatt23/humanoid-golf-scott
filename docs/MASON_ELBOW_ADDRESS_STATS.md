# Mason elbow-at-address statistics (for the reset-noise range)

Generated by `data/mason_elbow_address_stats.py` -> `data/references/mason_elbow_address_stats.json`. Tests: `tests/test_mason_elbow_address_stats.py`.
Everything is a 2-D MediaPipe proxy from ~30 fps screen-recorded feed video, **UNVERIFIED**.
Provenance: the Mason clips are derived from Mason's own screen-recorded social-media feed video; use of that data in a release needs Mason's consent (not yet given).

## Mapping to the env (read from code/XML only; nothing was run or edited)
- Reference column 2 = `right_elbow`, **degrees, flexion positive**. Env joint `right_elbow`: hinge axis `0 1 0`, range **0..150 deg** (`env/models/humanoid_golf_v4_power.xml`; `<compiler angle="degree">`). Same name, sign and units, so no transform. The env's reset sets `qpos[_q_el] = deg2rad(20) + U(-el_noise, el_noise)` (default `el_noise` = 0.1 rad) -> today's reset range is 14.3–25.7 deg = 0.249–0.449 rad, so **~30% of resets fall below the 0.31 rad failure threshold** (uniform assumption; the 0.31 threshold itself comes from the Orchestrator's seed-9000 report and was not reproduced here).
- Mapping confidence: high for name/sign/units; unverified that a 2-D video elbow flexion equals the humanoid's 3-D hinge angle.
- **Possible bug (not touched):** the imitation reward compares `reference["joints"]` to `qpos[14:14+11]` *positionally*. That lines up with the reference column order only for `humanoid_golf.xml` and `humanoid_golf_v2.xml`. In `humanoid_golf_v3.xml` / `humanoid_golf_v4_power.xml`, `qpos[14:]` starts with the hips (right_elbow is qpos 23, qpos 16 is right_ankle), so reference col 2 (elbow) is compared to the right ankle, col 0 (shoulder pitch) to the right hip, etc. I found this with mujoco's joint table; I did not run the env. Trainer/Evaluator should confirm; it may explain the ~0.07–0.09 tracking score.

## Recommendation
Candidates (clip to `[max(mean-k*std, 0.31+0.02 rad), min(mean+k*std, 150 deg)]`, mean/std from the 8 Mason clips):
| k | deg | rad | equivalent env base ± el_noise (rad) |
|---|---|---|---|
| k=1.0 | 21.8–33.3 | 0.381–0.581 | 0.481 ± 0.100 |
| k=1.5 | 19.0–36.1 | 0.331–0.631 | 0.481 ± 0.150 |
| k=2.0 | 18.9–39.0 | 0.330–0.681 | 0.505 ± 0.175 |

**Preferred: k=1.0, i.e. keep `el_noise=0.1` and move the elbow base from 20 deg (0.349 rad) to ~0.48 rad (27.5 deg)** -> range 0.381–0.581 rad. Justification: (1) it brackets the Mason median/IQR (23–30 deg); (2) its lower edge (0.381) is above the 0.31 failure threshold with 0.07 rad margin, so no reset can reach the failing region; (3) it needs a one-parameter change; (4) k=1.5/2.0 would hit the failure floor (0.33) on the low side and widen the range to 0.63–0.68 rad on data from only 8 clips.
If the Trainer wants to keep the current 20 deg base, the minimum fix is a base of >= 0.41 rad with `el_noise` 0.1 (lower edge 0.31 + margin), or clip the sample to >= 0.33 rad.

## Caveats (important)
- Mason's stored time axis often starts after takeaway began (`address_in_motion` for p1_s03, p1_s04 in `mason_keyframe_targets.json`; other clips begin at/near takeaway), so "address" is only a **prior**, probably biased to more flexion than real address (the early-window mean rises above the address value in most clips).
- Mason (27.5 deg mean) is higher than CMU (22.5) and MultiSense (14.3, wide spread 1–36). A real golfer's elbows are close to straight at address, so a video proxy of ~28 deg may over-state the humanoid's appropriate address elbow; the humanoid's club geometry (grip arm) may also need different elbow flexion. If seed-9000 failures only need elbow >= 0.31 rad, the data-matched range above satisfies that but should be validated in the env (not run here).
- n = 8 Mason clips, mostly down-the-line, 2-D, ~30 fps; std 5.7 deg is across clips/views, not measurement uncertainty.
